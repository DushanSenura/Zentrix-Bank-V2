# Zentrix Bank V2 — release notes (2.0.0, staging)

**Zentrix Bank V2 is a banking simulation.** Identities, accounts and money are fictional. It is not a licensed bank, holds no real funds,
and is not approved for production banking use. That would need independent security review, regulated integrations and authorization
that this project does not have.

## What V2 is
A rebuild of the V1 prototype as a full platform: a Flutter customer app, a React admin portal, a NestJS API on PostgreSQL with a
double-entry ledger, and a BullMQ worker.

* **Customer app:** registration and KYC, accounts with ledger-backed balances, PIN-confirmed payments (own, other customers, other banks,
  billers, QR; scheduled and recurring), beneficiaries, cards (debit, virtual, credit), fixed deposits, loans, savings goals and budgets,
  statements and receipts (PDF/CSV in English, Sinhala, Tamil), payment problem reports, support messages, branches and appointments,
  spending insights, a help assistant, notifications, security centre (sessions, devices, PIN/password, biometrics).
* **Admin portal:** permission-scoped dashboard, customer 360, KYC/account/card/loan reviews with two-person approval where money is involved,
  reversals and adjustments, staff and role management with escalation guards, risk alerts, support queues, reports with safe CSV export,
  settings and maintenance mode, audit log, system health.
* **Platform:** transactional outbox for notifications, idempotent payments, row-locked ledger, reminders, optional push gateway, optional
  AI wording for help answers and insights (isolated from payment authority).

## What changed since V1 (selected)
Server-verified PIN (V1 checked it on the device), hashed secrets, rotating refresh tokens with reuse detection, mandatory staff MFA,
real maker-checker, an append-only ledger instead of editable balances, deny-by-default authorization with tests that enumerate every route,
no demo passwords or developer bypasses outside development.

## Verified at this release
Typecheck and build clean; API 196 tests (against a real PostgreSQL test database), worker 5, admin 41, Flutter 89; `flutter analyze` clean;
dependency audit clean; staging stack built from scratch with Docker, migrated, smoke-tested (including register, sign-in and token refresh)
and its backup restored and compared with the live database; Android release APK built.

## Known limits — read before relying on anything
* **Never run on real hardware or a hosted environment.** The Flutter app has not been run on a device or emulator in this work, release
  builds have not been installed, and the staging stack was exercised only on one developer machine. No iOS build exists.
* **The admin portal was opened in a real browser only for its sign-in page.** Every other page was tested with jsdom and automated checks.
* **GitHub Actions has never run.** The workflow file is untested on GitHub.
* **No load, soak or failover testing; single instance of each service; no metrics or paging.** See `docs/deployment/monitoring.md`.
* **No external security assessment or penetration test.** Tests are the project's own.
* **Sinhala and Tamil wording is unreviewed** by a native speaker and PDF rendering of those scripts has not been inspected.
* **AI features have never called a real model**; push delivery is a generic webhook tested only against a fake gateway.
* **No email delivery** (invitations and password resets rely on out-of-band token handling in staging); invitations need
  `ALLOW_SETUP_TOKEN_IN_RESPONSE` in staging.
* **Android Lint's release check is skipped** because it crashes with the current toolchain (documented in `android-release.md`).
* Risk rules are simple simulated heuristics, not certified compliance controls.

See `PROGRESS.md` for the per-phase list of gaps.
